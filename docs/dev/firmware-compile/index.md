# Firmware Compile Documentation

Developer documentation for firmware-embedded runtime compilation, packaging, metadata, and integration contracts.

## Files

- **[runtime-packaging-contract.md](runtime-packaging-contract.md)** - Phase 1 runtime packaging contract: included file groups, canonical path mapping rules, target modules layout, runtime bootstrap strategy, immutable embedded metadata schema, and merge contract with dynamic upload metadata.
- **[embedded-metadata-api-contract.md](embedded-metadata-api-contract.md)** - Phases 8-9 embedded metadata and bootstrap setup API contract: runtime metadata retrieval, setup status/apply schemas, envelope markers, and host integration rules.
- **[staging-workflow.md](staging-workflow.md)** - Phase 2 implementation workflow for runtime staging into `ports/<target>/modules`, including one `TargetPackageContext` authority for variant selection, preflight checks, managed cleanup, deterministic copy, startup staging, metadata generation, the baked `device.json` identity, and dry-run reporting.
- **[package-selection.md](package-selection.md)** - Which node packages are frozen into an image and in which variant: the three package sources, the `global ∪ addons ∪ local` default, `--package-ids` and `--package-variants` semantics, capability gating, the one variant-decision authority, and the selection-related payload keys.
- **[archive-source-contract.md](archive-source-contract.md)** - The one "where is the archive?" rule for `addon.install`, `firmware.import`, `firmware.import-binary`, and the `mo addons` / `mo firmware` verbs: the path policy, the URL policy (https, loopback-only http, redirect budget, streamed byte cap, timeouts), the caller-chosen suffix policy (`.zip` for packages, `.bin` for a raw image), the ownership of a URL temp file, and the reproducible directory→zip packaging rule.
- **[server-firmware-api.md](server-firmware-api.md)** - Server firmware surface: the `GET /api/server-capabilities` payload (seven keys, `BackendDescriptor`, feature derivation), the loopback `Host`/`Origin` trust model and its rejection codes, and pointers to the job endpoint.
- **[firmware-build-websocket-protocol.md](firmware-build-websocket-protocol.md)** - `WS /firmware` frame contract: the client frames (including `firmware.import-binary`), the server frames, the stable error-code table, the unknown-field/unknown-type rules, the one-terminal-frame guarantee, and cancel/timeout/cleanup semantics.
- **[firmware-deploy-contract.md](firmware-deploy-contract.md)** - Headless firmware deploy: `flash_firmware`, `resolve_firmware_image`, backend selection precedence, the shared deploy payload, and the `flash-*` error-code family.
- **[backend-compile-interface-contract.md](backend-compile-interface-contract.md)** - General backend compile interface contract: invocation forms, arguments, output payload shape, failure/exit categories, safety guarantees, examples, and out-of-scope boundaries.
- **[build-backend-contract.md](build-backend-contract.md)** - Internal build-backend seam: `BuildBackend` protocol and value types, registry and entry-point discovery, `select_backend()` precedence, failure categories, `EspIdfBackend` behavior, stage events, and the M1/M3 streaming boundary.
- **[flash-backend-contract.md](flash-backend-contract.md)** - Internal flash-backend seam: `FlashBackend` protocol and value types, exit-code preservation, event vocabulary, the source-upload boundary, and the esptool command shape.
- **[process-streaming.md](process-streaming.md)** - The one seam every build/flash subprocess runs through: streamed `(stream, text)` lines, cancellation, timeout, and the `output`-frame mapping.
- **[build-pipeline-integration.md](build-pipeline-integration.md)** - Current phase-4 build pipeline orchestration sequence, packaging modes, artifact behavior, and troubleshooting by failure category.
- **[target-mapping-contract.md](target-mapping-contract.md)** - Target mapping contract: authoritative board source, canonical mapping artifact schema, wildcard/ambiguity rules, propagation fields, warning/error categories, and specific-target onboarding rules (compile-family filtering, unset bootstrap defaults, connect-time required selection).
- **[bootstrap-setup-validation-targets.md](bootstrap-setup-validation-targets.md)** - Validation targets for setup status/apply contracts, startup auto-setup idempotency, and host/view integration checks.
- **[runtime-json-generated-bootstrap-metadata-contract.md](runtime-json-generated-bootstrap-metadata-contract.md)** - Phase 11 generation contract: runtime-JSON-driven ownership for generated `embedded_metadata_payload.py` and `bootstrap_setup_templates.py`, diagnostics categories, migration break policy, and validation handoff inputs.
- **[firmware-versioning-and-artifact-publish-contract.md](firmware-versioning-and-artifact-publish-contract.md)** - Phase 13 contract: full firmware version identity, registry/lineage files, commit-msg hook orchestration, artifact publish semantics, `/opt` persistence baseline, and device/UI version visibility.
- **[firmware-inventory-contract.md](firmware-inventory-contract.md)** - Server-side local firmware inventory: listing published images with sidecar contents (including the frozen package variants and the imported-image provenance), the shared `isLatest` rule, the staleness comparison behind `mo firmware menu`, the `firmware.list` payload schema, the gated/path-guarded `firmware.delete` semantics, and the imported-image client rules.
- **[firmware-identity.md](firmware-identity.md)** - Canonical firmware identity reference: the semver grammar, the tag-derived derivation table, channel derivation, the content-hash payload (including the per-package variant) and exclusions, `release.json`, the registry/history schemas, and the imported-image identity (`imported` runtime id, placeholder version, content-hash discriminator).
- **[firmware-runtime-payload-contract.md](firmware-runtime-payload-contract.md)** - What one image carries end to end: runtime modes and detection, the frozen layout and relative-name invariant, the first-boot materialized `/`, the boot sequence, the deploy routing matrix, and the verification recipe.
- **[firmware-packages.md](firmware-packages.md)** - The self-contained `.firmware.zip` package: layout, the `firmware-package.json` descriptor, import validation, the `firmware.import` frame + `GET /api/firmware/package` route, the "import never builds or flashes" boundary, and the binary import (`imported_firmware.py`) that lands a raw `.bin` under the imported identity (web-only for now).
