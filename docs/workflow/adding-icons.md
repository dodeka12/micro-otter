# Adding Icons

Single workflow for adding an icon to Micro-Otter. Two icon sets are in use — **Google Material
Symbols** and **Material Design Icons (MDI)** — and the file goes to one of two places, depending on
what the icon is for. Read the table first; everything below is a shared recipe with per-set and
per-destination differences called out.

## Which workflow do I need?

| What you are adding | Icon set | File lands in | Registered in |
| --- | --- | --- | --- |
| **App/UI icon** (toolbar, panel, menu, button) | Google Material Symbols **or** MDI | `src/micro_otter/nodes/html/icons/` | `ICON_REGISTRY` in `js/views/icon-provider.ts` |
| **Node-type icon** (node palette and node card) | Google Material Symbols **or** MDI | `src/micro_otter/nodes/device/node_pkgs/<package>/icons/` (add-ons: `<package>/icons/` next to their `node_definitions.json`) | `"icon": "icons/<file>.svg"` in that package's `node_definitions.json` |
| **Home Assistant entity icon** | MDI **font only**, no SVG | *no file at all* | an `icon` control value such as `mdi:thermometer` |

The third row is not an SVG workflow. Skip to [Home Assistant entity icons](#home-assistant-entity-icons).

## Keep the three destinations apart

- **`src/micro_otter/nodes/html/icons/`** is the editor's own icon shelf. `IconProvider` maps a
  camelCase name to a filename and serves it from `/html/icons/`. Only icons that the editor UI
  itself displays belong here.
- **`node_pkgs/<package>/icons/`** belongs to one node package. The node system resolves the
  package-relative `icon` path from `node_definitions.json`; those files must **never** be added to
  `IconProvider`. See [node-definition-reference](../../docs/dev/nodes/node-definition-reference.md#icon-string).
- **`src/micro_otter/nodes/html/vendor/mdi/`** holds the vendored MDI **webfont** plus
  `icon-index.json`, generated by `tools/generate-mdi-icons.mjs` (`npm run generate:mdi`). It exists
  only so the `icon` control can offer a searchable `mdi:<name>` picker for Home Assistant entities.
  Do not point `IconProvider` or a `node_definitions.json` at it, and do not add glyphs to it by hand.

Both SVG destinations may hold icons from either set, side by side. The recipe only differs in where
the file is downloaded from and what the filename looks like.

## The two icon sets

### Google Material Symbols

- Browse: <https://fonts.google.com/icons> (choose the **outlined**, 24dp variant)
- File shape: `viewBox="0 -960 960 960"`, 960-unit glyph with optical padding
- Naming: snake_case upstream (`arrow_split`)
- Licence: Apache-2.0 — notice in `src/micro_otter/nodes/html/icons/LICENSE`
- Already attributed in Info → About (see [Attribution](#attribution))

### Material Design Icons (MDI, Pictogrammers)

- Browse: <https://pictogrammers.com/library/mdi/> — an icon page is
  `https://pictogrammers.com/library/mdi/icon/<name>/`
- File shape: `viewBox="0 0 24 24"`, glyph fills the box edge to edge
- Naming: kebab-case upstream (`arrow-split`)
- Pinned version: **MDI 7.4.47**, the version of the vendored webfont
  (`MDI_VERSION` in `tools/generate-mdi-icons.mjs`). `@mdi/svg@7.4.47` is a dev dependency, so the
  full SVG set is already on disk after `npm ci`
- Licence: Apache-2.0 / Pictogrammers Free License — notice in
  `src/micro_otter/nodes/html/vendor/mdi/LICENSE`
- Already attributed in Info → About through the `@mdi/font` entry

Visually, an MDI glyph at 24 px looks slightly larger than a Material Symbols glyph of the same box,
because Symbols keeps optical padding around the shape. Compare the new icon with its neighbours
before committing.

## Step 1 — Download the SVG

### Google Material Symbols

```bash
curl -sSL "https://fonts.gstatic.com/s/i/short-term/release/materialsymbolsoutlined/{icon-name}/default/24px.svg" \
  -o "src/micro_otter/nodes/html/icons/{icon_name}_24dp.svg"
```

```powershell
Invoke-WebRequest -Uri "https://fonts.gstatic.com/s/i/short-term/release/materialsymbolsoutlined/{icon-name}/default/24px.svg" -OutFile "src\micro_otter\nodes\html\icons\{icon_name}_24dp.svg"
```

Replace `{icon-name}` with the name shown on the icon page (e.g. `cable`, `arrow_split`).

### Material Design Icons

Preferred — the pinned local copy, offline and version-locked to the vendored font:

```bash
ls node_modules/@mdi/svg/svg/ | grep '^arrow'          # confirm the exact name first
cp node_modules/@mdi/svg/svg/arrow-split.svg \
   src/micro_otter/nodes/html/icons/arrow_split_24dp.svg
```

Fallback when `node_modules` is not installed — the same pinned release from the CDN:

```bash
curl -sSL "https://cdn.jsdelivr.net/npm/@mdi/svg@7.4.47/svg/arrow-split.svg" \
  -o "src/micro_otter/nodes/html/icons/arrow_split_24dp.svg"
```

```powershell
Invoke-WebRequest -Uri "https://cdn.jsdelivr.net/npm/@mdi/svg@7.4.47/svg/arrow-split.svg" -OutFile "src\micro_otter\nodes\html\icons\arrow_split_24dp.svg"
```

Notes:

- There is **no public Pictogrammers REST/GraphQL API** — `api.pictogrammers.com` only redirects and
  has no `/graphql` endpoint. Use the pinned npm package (or its jsDelivr mirror) plus the website's
  search box.
- Never download from `raw.githubusercontent.com/Templarian/MaterialDesign/master/…`: that branch
  moves, so the file you get today is not the file the next contributor gets.

## Step 2 — Normalize the SVG

Both sets need the same three edits:

1. **Add `fill="#e3e3e3"` to the root `<svg>`.** Downloaded SVGs are black or have no fill; every
   Micro-Otter icon starts from the same light grey so the toolbar CSS (brightness/grayscale
   filters) behaves uniformly.
2. **Keep the file on one line.** The existing icons are single-line files; a pretty-printed SVG
   makes the diff unreadable.
3. **Rename to snake_case + `_24dp.svg`.** Google names are already snake_case; MDI names are
   kebab-case (`arrow-split` → `arrow_split_24dp.svg`).

```xml
<!-- Before (Google) -->
<svg xmlns="http://www.w3.org/2000/svg" height="24" viewBox="0 -960 960 960" width="24"><path d="..."/></svg>

<!-- After (Google) -->
<svg xmlns="http://www.w3.org/2000/svg" height="24" viewBox="0 -960 960 960" width="24" fill="#e3e3e3"><path d="..."/></svg>
```

```xml
<!-- Before (MDI 7.4.47) -->
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24"><path d="..."/></svg>

<!-- After (MDI 7.4.47) -->
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="#e3e3e3" id="mdi-arrow-split"><path d="..."/></svg>
```

- **Keep an MDI `id="mdi-<name>"` attribute** when the download carries one: it is free provenance
  and harmless, because every icon is loaded as an `<img src="…">` document (a file URL, or the
  generated `data:` URI), so each SVG stays a separate document and ids cannot collide in the DOM.
- **Watch for name collisions.** MDI and Material Symbols share many names, and a snake_cased MDI
  icon can land on an existing Google file (e.g. `arrow_split_24dp.svg` already exists in
  `html/icons/`). Two files with the same name in two node packages are fine; a silent overwrite in
  one directory is not — check `git status` before adding.

## Step 3 — Put the file in the right folder

| Destination | Path |
| --- | --- |
| App/UI icon | `src/micro_otter/nodes/html/icons/<icon_name>_24dp.svg` |
| Node-type icon | `src/micro_otter/nodes/device/node_pkgs/<package>/icons/<icon_name>_24dp.svg` |
| Node-type icon in an add-on package | `<package>/icons/<icon_name>_24dp.svg`, beside that package's `node_definitions.json` (e.g. `examples/addons/node_pkgs/pulse/icons/`) |

Both directories are copied as-is by Vite (`html/icons` through `vite-plugin-static-copy`, package
icons inside the package tree), so a new file needs no build configuration. An add-on's `icons/`
folder needs none either: `mo addons install` copies the whole package directory and
`mo addons package` zips every file in it.

## Step 4 — Register the icon

### App/UI icons — `IconProvider`

File: `src/micro_otter/nodes/html/js/views/icon-provider.ts`

Add the filename to `ICON_REGISTRY` in the matching category block, and (optionally) a typed getter:

```typescript
const ICON_REGISTRY = {
    // ... existing icons ...

    // Connectivity
    cable: 'cable_24dp.svg',
};

// Getter, for direct access from views
static get cable(): string {
    return this.get('cable');
}
```

Use it with `IconProvider.cable`, or dynamically with `IconProvider.has(name)` /
`IconProvider.get(name)`. `get()` throws for an unknown name, so guard dynamic lookups with `has()`.

Then regenerate the inlined icon module — nothing does it for you at build time:

```bash
npm run generate:icons
```

`tools/generate-inlined-icons.mjs` reads every registered `.svg` and rewrites
`js/views/icon-data.generated.js`; commit that file. `npm run check:icons-generated` (part of
`check:ci-local`) regenerates it and fails when the committed module is stale.

`IconProvider.get(name)` answers a `data:image/svg+xml;base64,…` URI for every registered `.svg`, so
an icon renders without a network request — which is what keeps menus, toolbars, and the title-bar
offline badge intact while the local server is down. `IconProvider.getPath(name)` still answers
`/html/icons/<file>` for consumers that need a URL, and the PNG/ICO brand images keep the path form in
both methods: the generated module covers registered `.svg` files only.

Because of that split, never classify an icon value by its file extension. Ask
`IconProvider.isImageSource(value)` when a component has to choose between an `<img>` and a
text/emoji glyph: it accepts the inlined `data:` URI, any other URI scheme, a rooted or relative
path, and a value ending in an image extension. `TabbedView`, `MenuView`, `OverlayWindow`,
`ModalDialogView` and the `WorkspaceView` title-bar buttons all use it — an extension-only test
treats an inlined icon as text and prints the whole base64 document into the UI.

### Node-type icons — `node_definitions.json`

No `IconProvider` entry. Reference the package-relative path:

```json
{
    "web-view-tile": {
        "icon": "icons/tile_small_24dp.svg"
    }
}
```

The node system resolves the path relative to the package root; nothing else to wire up.

## Naming convention

| Layer | Convention | Example |
| --- | --- | --- |
| File on disk | snake_case + `_24dp.svg` | `serial_connect_24dp.svg` |
| MDI upstream name | kebab-case | `serial-port` |
| `IconProvider` registry key | camelCase | `serialConnect` |
| `IconProvider` getter | same as the key | `IconProvider.serialConnect` |
| Node definition path | `icons/<file>` | `icons/tile_small_24dp.svg` |
| Home Assistant value | `mdi:<upstream-kebab-name>` | `mdi:thermometer` |

Keep the registry grouped by purpose so the file stays navigable: **Actions**, **Navigation & UI**,
**Connectivity**, **File operations**, **Development**, **Status & feedback**, **Device & hardware**,
**Branding**, **Node Palette**.

## Home Assistant entity icons

This is the one case with **no SVG file**. A `hass` entity's `icon` control holds a Home Assistant
icon string — `mdi:thermometer` — and Home Assistant renders it from the MDI webfont it already
ships. Micro-Otter only helps you pick the name:

- the picker searches the vendored index `src/micro_otter/nodes/html/vendor/mdi/icon-index.json`
  (loaded lazily by `js/data/mdi-icons.ts`), which is generated from `@mdi/svg/meta.json` by
  `npm run generate:mdi`;
- a name that is not in the index (MDI newer than 7.4.47, or a foreign set such as `ph:`) is still
  accepted — the control is free text — but the graph rule `hass-icon-invalid` warns about it;
- **do not** download an MDI glyph into `html/icons/` or a package `icons/` folder to "make an
  entity icon work": the entity icon is resolved by Home Assistant, not by the editor.

See [hass-node-system](../../docs/dev/nodes/hass-node-system.md) for the control contract and the
`mdi:<name>` grammar.

## Attribution

Both sets are already attributed in the editor's **Info → About** dialog, so adding an icon needs no
licence bookkeeping. The rows come from one file:

`tools/open-source-package-overrides.json`
→ `npm run generate:oss` (`tools/generate-open-source-packages.mjs`)
→ `js/core/open-source-packages.generated.js`
→ `OPEN_SOURCE_PACKAGES` in `js/core/app-meta.ts` → `AboutDialogView`.

The generator collects `dependencies` from `package.json` and the jsDelivr `<script>` URLs in
`index.html`, and requires a matching override entry for each; that is why MDI is already listed
through `@mdi/font`. Sets that are vendored as **loose files** are invisible to that scan and are
listed explicitly in the reserved `vendoredAssets` array of the same JSON — currently
`Google Material Symbols` (Apache-2.0, linked to the upstream `LICENSE`).

Only if you introduce a **new** icon set:

1. add a `vendoredAssets` entry (`name`, `license`, `url` — link the licence, not the marketing page);
2. drop the upstream licence text next to the files, with a header naming the covered directories
   and the modification (`fill="#e3e3e3"`), following `src/micro_otter/nodes/html/icons/LICENSE`;
3. run `npm run generate:oss` and commit the regenerated module
   (`npm run check:oss-generated` is the CI gate).

## Validation checklist

- [ ] The file is in the correct folder for its purpose (app icon *or* package icon — not both)
- [ ] The root `<svg>` carries `fill="#e3e3e3"`
- [ ] The file is single-line and named `<icon_name>_24dp.svg`
- [ ] An app icon is registered in `ICON_REGISTRY`; a node icon is referenced in `node_definitions.json`
- [ ] For an app icon, `npm run generate:icons` ran and `js/views/icon-data.generated.js` is committed
- [ ] `git status` shows a new file, not only a modified one (no accidental overwrite)
- [ ] The icon renders next to its neighbours without looking oversized
- [ ] `npm run lint && npm run test:node` pass

## Troubleshooting

**404 on the Google URL** — the icon name on the website differs from the download path. Copy the
name from the icon page (`arrow_split`), not from the search result.

**404 on the MDI CDN URL** — MDI names are kebab-case and the tool cannot guess them:
`ls node_modules/@mdi/svg/svg/ | grep '^arrow'` lists the real names.

**Icon does not appear** — check the browser console for a 404, then compare the registered filename
byte for byte with the file on disk.

**Icon looks too big or too bold** — MDI glyphs fill their `0 0 24 24` box, Material Symbols keep
optical padding inside a `0 -960 960 960` box. Either pick a Symbols icon for the same purpose or
accept the difference deliberately.

**`IconProvider.get()` throws** — the name is missing from `ICON_REGISTRY`; `get()` lists the
available names in the error message.

**A long `data:image/svg+xml;base64,…` string shows up as text** — the caller classified the icon
value by file extension and fell into its text/emoji branch. Use `IconProvider.isImageSource(value)`
to choose between `<img>` and text, as described in
[Step 4](#appui-icons--iconprovider).
