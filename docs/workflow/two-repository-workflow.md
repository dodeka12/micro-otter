# Workflow: routing a change through two repositories

Which branch, which pull request, and when to publish. The model behind it is in
[../admin/two-repository-model.md](../admin/two-repository-model.md); the guard reference is in
[../admin/release-sync.md](../admin/release-sync.md).

You only ever write **one** pull request by hand. The second one is generated by `publish.mjs`.

## Step 0 — Classify every changed file

```bash
git status --short
```

| Path starts with | Class | Reaches the public repository |
|---|---|---|
| `ldev/` | private only | never |
| anything else that is tracked | product | on the next publication |
| `.venv/`, `node_modules/`, `_dist/`, generated versions | local build state | never — do not commit |

A branch may mix both classes. Publication keeps the product files and drops `ldev/` silently; there is
no per-file decision and nothing to undo.

If **every** changed path is private-only, the branch is a *private-only branch* (Step 4).

## Step 1 — Branch (always, both classes)

```bash
git switch main && git pull
git switch -c <type>/<slug>        # docs/readme-slim · feat/m7-wheel · fix/serial-timeout
```

- `<type>` is the Conventional Commit type: `feat`, `fix`, `docs`, `refactor`, `chore`, `ci`, `test`.
- The branch name is the changelog filename: `docs/changelog/YYYY/MM/DD_<type>-<slug>.md`.
- Product changes need that changelog entry; private-only changes do not.

## Step 2 — Commit, then run the gates

```bash
git add <only the intended files>
git commit -S -m "<type>(<scope>): <summary>"     # signed; never --no-gpg-sign

npm run check:ci-local && npm run test:node && npm run typecheck && uv run pytest -q
```

If gpg cannot prompt for the passphrase, stop and hand the command to the user rather than bypassing
signing.

## Step 3 — PR A: the private repository (always)

```bash
git push -u origin <branch>
gh pr create --base main --title "<type>: <summary>" --body-file /tmp/pr-body.md
gh pr merge --squash --delete-branch              # squash at merge, never locally
```

Write the body first (the `pull-request-workflow` skill has the template). Wait for CI (`python`,
`docs`, `web`) before merging. After the merge:

```bash
git switch main && git pull
```

## Step 4 — Decide whether to publish

| Branch contained | PR A | `publish.mjs` | PR B |
|---|---|---|---|
| `ldev/` only (plans, handoffs, tracker rows) | yes | **no** — `status` prints *nothing unpublished* | no |
| product only | yes | **yes** | yes |
| both | yes | **yes** — `ldev/` is dropped | yes |

Publishing is optional in principle and mandatory in practice: an unpublished product change is
invisible to users and to the public repository's CI.

**Publish now, not later, when** the pending delta is still one coherent story. `node
ldev/tools/publish.mjs status` lists it; a delta spanning unrelated topics is harder to review as one
publication.

## Step 5 — Publish and PR B

Run from a **clean, up-to-date private `main`**:

```bash
node ldev/tools/publish.mjs status
node ldev/tools/publish.mjs prepare --title "<type>: <summary>"
node ldev/tools/publish.mjs publish --create-pr
```

- `prepare` writes into `../micro-otter` (the public clone, `upstream` = `micro-otter`) and prints the
  exact `publish` line, including the branch it created.
- `publish --create-pr` pushes that branch and opens PR B. You do not edit its body; the tool builds it
  from the squashed private commit subjects.
- PR B's diff is the product delta only. If a file you expected is missing, it was `ldev/` — that is
  correct. If a file you did *not* expect is there, stop and check `status`.

Then merge PR B on the public repository (`python`, `docs`, `web` must pass). The merge is the
publication. Tagging is **manual** and belongs to the release procedure
([../workflow/release.md](release.md)): `bump-version.yml` no longer runs on a merge, so create the
tag with the release you actually assemble. The public
`main` asks for an approving review and GitHub forbids self-approval, so a single maintainer merges with
the ruleset bypass: `gh pr merge <number> --squash --admin`.

## Step 6 — Sync down (always after PR B merges)

```bash
git fetch upstream --tags
git merge upstream/main        # no shared file differs, so this should be a clean merge
git diff --stat upstream/main HEAD -- . ':(exclude)ldev' ':(exclude)agents-local.md'   # no output
node ldev/tools/publish.mjs status    # nothing unpublished
```

Skipping this makes the next `prepare` fail with the `sync-down` guard, which exists because publishing
a stale tree would revert public commits.

## The whole sequence, in order

```bash
# 1. private branch + PR A
git switch main && git pull && git switch -c docs/example
git add <paths> && git commit -S -m "docs: example"
npm run check:ci-local && npm run test:node && npm run typecheck && uv run pytest -q
git push -u origin docs/example
gh pr create --base main --title "docs: example" --body-file /tmp/pr-body.md
gh pr merge --squash --delete-branch
git switch main && git pull

# 2. publication + PR B  (product changes only)
node ldev/tools/publish.mjs status
node ldev/tools/publish.mjs prepare --title "docs: example"
node ldev/tools/publish.mjs publish --create-pr
#    merge PR B on the public repository

# 3. sync down
git fetch upstream --tags
git merge upstream/main
node ldev/tools/publish.mjs status
```

## Rules that bite

1. **Never publish before PR A is merged.** `publish.mjs` takes the files at the private `HEAD`, so
   publishing from a feature branch publishes that unmerged branch.
2. **Never publish with a dirty tree.** The `clean private tree` guard refuses it (exit `2`) — commit
   first, including plan files, which is why they usually ride along on the same branch.
3. **Never open a PR against the public repository by hand.** The only branches it should ever carry are
   the tool's `publish/<slug>` branches.
4. **Never skip the sync-down merge.** It is what keeps the two repositories comparable.
5. **Do not rewrite the public branch.** A force-push invalidates an open PR (GitHub will not reopen
   it); close it and publish again with a fresh branch.

## Troubleshooting

| Symptom | Meaning | Action |
|---|---|---|
| `status` exits `2`, `clean private tree` | uncommitted or untracked change | commit it (or delete build output) |
| `status` exits `2`, `sync-down` | public `main` has a commit this tree lacks | `git merge upstream/main`; a non-empty `git diff --stat upstream/main HEAD -- ':(exclude)ldev' ':(exclude)agents-local.md'` afterwards means the merge dropped or missed a product change |
| `status` exits `2`, `leak` | an `ldev/` or untracked path reached the delta | check `untrackedPaths` in `ldev/tools/publish-config.json`; never `git add` build output |
| `status` exits `2`, `forbidden strings` | published text names the private repository | remove the literal from that file |
| `prepare` refused, branch has an open PR | a rewrite of a reviewed publication | close PR B, publish a new branch |
| `status` says *nothing unpublished* | everything is already public | nothing to do |
